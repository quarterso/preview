Handling states

What your code should do for each state execute can return, and for a lost response from Quarter itself.

execute returns 200 when the action ended with a known outcome and 202 when it is still open. Uncertainty is data, not an exception: the SDK resolves both, and only errors (4xx) throw. Branch on state.

Summary

StateHTTPWhat to do
CONFIRMED200Done. Store output.providerObjectId and, if you keep records, proof.
NOT_EXECUTED200Nothing happened. Read reason, fix the cause, and decide whether this is a new operation.
SAFE_TO_RETRY202Call execute again with the same intent.
OUTCOME_UNKNOWN, RECONCILING202Do not retry. Wait for a webhook or poll.
NEEDS_REVIEW202Route to a person. Resolve with evidence.
AUTHORIZED, EXECUTING202Still running. Wait for a webhook or poll.
COMPENSATED200The effect was undone by a compensator. Treat as not in effect.

A complete handler

CONFIRMED

The provider object exists and holds what you asked for. assurance says how that was established. Nothing further will change the action unless a compensator runs.

NOT_EXECUTED

The write did not happen, and there is evidence for that. From execute, this is usually a provider rejection (reason: PROVIDER_REJECTED), such as a refund larger than the charge. Reconciliation can also end here when a lookup proves absence. Sending the same intent again returns the same NOT_EXECUTED action. If you fix the input, it is a different write: give it a new id.

Invalid input and policy denials also end in NOT_EXECUTED, but execute reports them as errors (VALIDATION_FAILED 422, POLICY_DENIED 403) with the action view in error.details.action. See Errors.

SAFE_TO_RETRY

Quarter has proven that the write did not take effect and that another attempt cannot duplicate it. Quarter retries on its own while the spec's retry budget allows (with backoff, and honoring provider rate limit headers after a 429). You receive SAFE_TO_RETRY when that budget is used up, or after an operator resolved an action to it. Calling execute with the same intent schedules the next attempt with the same idempotency key.

OUTCOME_UNKNOWN and RECONCILING

The attempt may have reached the provider and the answer was lost. Quarter is finding out. Do not send a new write, and do not treat this as failure. Calling execute again is safe but does nothing: Quarter records RETRY_SUPPRESSED and returns the same state.

Wait for action.confirmed, action.not_executed, action.safe_to_retry or action.needs_review on your webhook, or poll GET /v1/actions/{actionId} with backoff. For AR3 actions reconciliation usually ends within the spec's maxElapsedMs (90 seconds for most).

NEEDS_REVIEW

Automation cannot decide safely. Either reconciliation ran out of budget, the provider reported success but the object does not match, or a policy rule requires approval. reason says which.

A person checks the provider and resolves the action with evidence. Resolutions are audited and never erase the history before them. If a policy held the action before anything was sent (the action.approval_required event), use approve or reject instead.

ResolutionUse whenRequires
CONFIRMEDThe object exists at the provider.evidence.providerObjectId
NOT_EXECUTEDThe write is proven absent and should not happen.A note saying what proves it
SAFE_TO_RETRYThe write is absent and should go ahead. Also releases a policy hold, though approve is the direct route.A note; then call execute again

If a provider lookup was down when reconciliation ran, POST /v1/actions/{actionId}/reconcile runs the budget again instead of resolving by hand. It works from OUTCOME_UNKNOWN and from NEEDS_REVIEW after a dispatched attempt.

AUTHORIZED and EXECUTING

The action is queued or running. In managed mode, execute waits up to ?wait= milliseconds (default 10000) before answering, so you see these states only for slow providers. In executor mode execute answers immediately, because the customer-side executor claims the work on its own schedule. Wait for the webhook.

When the response from Quarter is lost

A timeout or reset between your service and Quarter leaves you not knowing whether Quarter accepted the intent. The SDK raises QuarterTransportError with maybeExecuted: true for a POST in that case, and for a POST answered with a 5xx. It never retries POSTs on its own. Resend the identical intent. Quarter returns the existing action; it does not run it twice. Never mint a new id to recover.
