Get started

Quarter documentation

Try Quarter in the simulated sandbox in five minutes, then send provider writes through it, read the state it returns, and react to outcomes.

Quarter runs important writes to the APIs your app depends on, keeps a retry from repeating them, and tells you what happened with evidence. The fastest way to see it is the simulated sandbox: no provider account, five minutes.

Five-minute quickstart

Log in with a sandbox key, run a Stripe refund, make the next response disappear, run another refund, and watch Quarter prove it happened once. The Quickstart explains each step.

What Quarter does

Quarter runs important writes to the APIs your app depends on: payments, billing, commerce, CRM, support, email, identity, data and scheduling. 38 providers are supported today, from Stripe and Shopify to HubSpot, Zendesk, Clerk and Supabase. Each write has a stable identity you choose, runs at most once, and ends in a state backed by evidence. When a provider response is lost, Quarter checks the provider and tells you what happened instead of guessing.

Start here

  • Quickstart: see a lost response resolved in the simulated sandbox.
  • Send an action from code: install the SDK, send a refund, read its state.
  • Python SDK: the same client for Python, sync and async.
  • Concepts: action identity, states, reliability classes, evidence and Outcome Proof.
  • Handling states: what your code does for each state.

Build

  • Operations: several actions in order, with compensation and review pauses.
  • Recipes: named business actions, such as deleting an account, run as one operation with one signed proof.
  • SDK integrations: wrapStripe, Temporal, Inngest, Trigger.dev, and a Next.js webhook route.
  • Simulated sandbox and test helpers: inject provider faults and read what really happened.
  • Idempotency keys: safe retries of any request to Quarter's own API.
  • Use Quarter from AI coding tools: the MCP server, /llms.txt, and Markdown docs.

React to outcomes

  • Webhooks: signed deliveries when an action settles.
  • Events and streaming: list past events or stream them as they commit.
  • Signed proofs: fetch an Outcome Proof and verify it offline.
  • Ledger search and export: search by metadata, export CSV.

Operate

  • Customer-side executor: run provider calls inside your network with your own credentials.
  • Shadow mode and ActionLint: measure risky writes before you route them through Quarter.
  • Policies, API keys, audit log: project controls.
  • Errors: every error code and what to do about it.

Reference

  • API reference: every endpoint, with request and response examples.
  • Actions reference: every supported action, generated from its ActionSpec.
  • CLI reference: every quarter command and flag.
  • How providers are supported: the three proof paths, and what next and researched mean.

Conventions

  • Examples use https://api.example.test as a placeholder base URL. Your early access onboarding gives you the real one. The SDK and the curl examples read it from QUARTER_API_URL.
  • All request and response bodies are JSON. Timestamps are ISO 8601 in UTC.
  • Every response carries a quarter-request-id header. Include it when you report a problem.
  • Action ids can contain :. URL-encode them in paths: refund:order_1042:v1 becomes refund%3Aorder_1042%3Av1.
