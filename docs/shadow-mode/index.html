Operate

Shadow mode and ActionLint

Find risky provider writes in your code with ActionLint, record how they behave in production with shadow mode, and combine both into a reliability report.

Before routing writes through Quarter you can measure them. ActionLint finds risky writes statically. Shadow mode records what happens when your code makes them. POST /v1/audit/analyze combines both into a Critical Action Reliability Report. Neither changes how your code runs.

ActionLint

ActionLint is a static analyzer for TypeScript and JavaScript. It reports provider mutations that can run twice or be lost.

Options: --format text|json and --fail-on high|medium|low (default low). Exit code 1 means a finding met the --fail-on confidence; exit code 2 is a usage error. Run it in CI with --fail-on high to block new unprotected writes.

RuleFinds
no-stable-identityTwilio sends, Salesforce sobject().create, Stripe idempotency keys that change per run.
missing-native-idempotencyStripe writes without idempotencyKey, Shopify mutations without @idempotent.
retry-around-mutationThose writes inside a retry loop or retry helper.
fresh-key-in-retryrandomUUID(), Date.now() and similar keys created inside a retry.
retry-outbound-postfetch or axios POSTs retried without an idempotency header.
async-treated-completeA 202 or Graph sendMail followed by marking the work complete.

Each JSON finding has rule, file, line, column, risk, confidence (high, medium, low), message, recommendation, and when it can tell, provider and a guessed action such as stripe.refund.create. Confidence describes how sure the static match is, not how dangerous the write is.

Shadow mode

quarter.shadow wraps a provider call your code still makes itself. It runs the call, returns its result or rethrows its error unchanged, and records an observation in the background: the intent, how the call ended, and how long it took.

The SDK classifies the outcome from the HTTP status on the result or error (status or statusCode):

OutcomeRecorded as
A result without a status, or any status other than those belowdispatched_response
429throttled
5xx or 408ambiguous
An error without any statusambiguous, because it cannot prove the request never left
  • When your code retries a call, set retryOf to identify the earlier attempt, so the report can link retries to one operation.
  • Observation failures never reach your call path. They go to onObserveError in the client options, which logs a warning by default.
  • Use the same id scheme you will use with execute. The report counts distinct ids per action type to show whether your identities are stable.

Without the SDK, send the observation yourself. The endpoint answers 202 and stores it; it never calls the provider.

The reliability report

POST /v1/audit/analyze takes ActionLint findings (up to 5000) and combines them with the last 30 days of shadow observations for the project.

FieldMeaning
retryHazardsFinding counts by risk.
identityCoveragePer action type: observations, distinct action ids, and retries linked with retryOf.
observedAmbiguityAction types that saw ambiguous or throttled outcomes in production.
protectionCandidatesSupported action types, ordered by observed ambiguity plus static findings. Start with the first one.
unsupportedWritesAction types found or observed that have no ActionSpec yet.
