Operate

Customer-side executor

Run provider calls inside your own network. The executor pulls signed plans, runs installed adapters with local credentials, and returns signed facts.

A project runs in one of two execution modes. In managed mode, Quarter's workers call the provider. Managed mode is for sandbox projects and refuses live provider keys. In executor mode, a process you run calls the provider, and provider credentials never leave your environment. Production projects use executor mode.

How it works

  1. Your service calls execute as usual. Quarter validates, applies policy, compiles the plan and answers at once with 202.
  2. The executor polls POST /v1/executor/jobs/claim over outbound HTTPS. It gets a job: the input, and a plan envelope signed by Quarter with Ed25519 that expires after 60 seconds.
  3. The executor checks the envelope, runs the provider call with local credentials, and redacts the provider response with the spec's allowlist.
  4. It signs the result with its own key and sends it to POST /v1/executor/jobs/result. Quarter decides the next state from that fact.

Reconciliation lookups run the same way: Quarter hands the executor a signed reconciliation job and the executor reports what the provider returned. The executor needs no inbound ports.

Enrollment

Quarter issues a one-time enrollment secret (qe_...) for an executor-mode project. On first start the executor generates an Ed25519 key pair, sends the secret and its public key to POST /v1/executor/enroll, and receives an executor token (qx_...). The secret cannot be used again.

The private key and token are stored in ~/.quarter-executor with mode 0600. Set QUARTER_EXECUTOR_STATE to use another directory, such as a mounted volume. On later starts the executor reuses them and the enrollment secret is not needed. To replace an executor, enroll a new one with a new secret.

What it will refuse

The executor runs only what it can verify and has installed. It refuses a job when:

  • the plan signature does not verify against a published Quarter key (GET /v1/executor/keys, fetched once over TLS or pinned);
  • the envelope has expired;
  • it has no adapter for the action type;
  • the plan's specVersion differs from the ActionSpec version it ships.

A refused execute job is reported as not_dispatched with error code EXECUTOR_REFUSED:<reason>, which is a fact: nothing reached the provider. A refused reconciliation job is reported as inconclusive. The executor never accepts code, shell commands, URLs or actions from the control plane. It runs the adapter code in its own installed version, with the input from the job.

The executor reads provider credentials from its environment. Quarter never sees them, and the plan never contains them.

Configure every provider the project sends actions to. If a job arrives for a provider without credentials, the executor logs an error and reports nothing. The lease then expires and the action is reconciled like any other interrupted attempt.

Operating the executor

  • Run at least two executors per project for availability. Claims are leased, so two executors never run the same attempt.
  • An executor that dies mid-attempt loses its lease. The action becomes OUTCOME_UNKNOWN with reason LEASE_EXPIRED and is reconciled.
  • The executor stops cleanly on SIGINT and SIGTERM.
  • When Quarter rotates its plan signing key, the old public key stays published until executors have picked up the new one.
  • Upgrade executors when you upgrade ActionSpec versions. An executor with an older spec refuses plans compiled against a newer one.
