Operate

Policies, API keys, audit log

Gate actions with a versioned policy, manage project API keys, and read the audit log of administrative changes.

Policies

A policy is a list of rules evaluated for every new action after input validation. Each project points at one policy version. Rules match on action: an exact type (stripe.refund.create), a provider (stripe.*), or everything (*).

RuleFieldsEffect when it matches
deny_actionactionDenied. The action ends NOT_EXECUTED and execute returns 403 POLICY_DENIED.
require_actor_typeaction, actorTypesDenied unless actor.type is one of actorTypes (user, service, workflow, agent).
review_aboveaction, field, thresholdWhen the numeric input field is above threshold, the action goes to NEEDS_REVIEW before dispatch.

A deny beats a review, and a review beats authorize. Every rule that matched is recorded in the plan as a gate (<policy id>@<version>:<kind>), so the plan hash changes when the policy that applied changes.

Policies are immutable. PUT /v1/policy writes version n+1 and points the project at it; it does not edit the current version. Actions already compiled keep the gates they were compiled with. The optional id (lowercase letters, digits and dashes) names the policy; it defaults to the current one, or default. A policy holds up to 100 rules.

To avoid overwriting a change someone else made, send expectedVersion with the version you read from GET /v1/policy (null when the project has no policy yet). If the project has moved on, the update fails with 409 VERSION_CONFLICT: read the policy again and reapply your change.

To answer an action held by review_above, call POST /v1/actions/{actionId}/approve to release it for dispatch, or /reject to end it as NOT_EXECUTED. The approver is recorded in the ledger and in the proof as approvedBy. See NEEDS_REVIEW.

API keys

Keys belong to a project and inherit its environment: qk_test_ for sandbox, qk_live_ for production. Send them as authorization: Bearer <key>. Quarter stores a hash and the first 16 characters as prefix, so a key is shown exactly once, in the create response.

  • Rotate without downtime: create a key, deploy it, then revoke the old one.
  • Quarter refuses to revoke the last active key of a project, with 422 VALIDATION_FAILED.
  • A revoked or unknown key gets 401 UNAUTHORIZED on every request.
  • GET /v1/api_keys lists id, prefix, createdAt and revokedAt for each key. It never returns the key.

Audit log

Administrative changes are recorded in an append-only audit log. The database rejects updates and deletes on it.

actionRecorded when
policy.updateA new policy version is written. data has id, version and the rule count.
api_key.createA key is created. data has its id.
api_key.revokeA key is revoked. data has its id.
action.resolveAn operator resolves an action. data has actionId, from, to and reason.
provider_webhook.configureA provider webhook secret is set. data has the provider.
spec_block.clearA spec block is cleared. data has its id and the reason.

actor is request:<quarter-request-id> for API changes, which you can match against GET /v1/requests, or the operator name given when an action was resolved.

Provider webhooks

Stripe, Shopify and Twilio can notify Quarter directly. Quarter treats a provider webhook as a lead, never as proof: it verifies the provider's signature, records the event once, attaches it to matching open actions as heuristic evidence, and reopens their reconciliation so a deterministic lookup decides. This shortens the time an action spends in OUTCOME_UNKNOWN or NEEDS_REVIEW.

Store the signing secret the provider gave you, then point the provider at the returned path under your Quarter base URL.

GET /v1/provider_webhooks (quarter.providerWebhooks.list()) lists configured providers with updatedAt and the path. The secret is never returned. Setting it again replaces it.

Every webhook is verified against the stored secret before anything is recorded. A missing or wrong signature, or a provider with no stored secret, gets 401 UNAUTHORIZED.

ProviderSignature checkMatched to open actions by
Stripestripe-signature: HMAC-SHA256 of <t>.<raw body> in v1; t must be within 300 seconds.The Quarter action id in the object's metadata.
Shopifyx-shopify-hmac-sha256: base64 HMAC-SHA256 of the raw body.Order id.
Twiliox-twilio-signature: base64 HMAC-SHA1 of the full URL followed by each form parameter name and value, sorted by name.The To number.

Twilio signs the URL it called, so a proxy in front of Quarter must keep the host header and set x-forwarded-proto. A repeated event is recorded once and answered with duplicate: true. A matched event never settles an action by itself: it is heuristic evidence, and the reopened reconciliation must find the object at the provider.

Spec blocks

Each ActionSpec is tested against one provider API version, its providerApiVersion. Version drift is when a provider answers an attempt with a different version. Quarter then opens a spec block for that action type in your tenant, recording the expected and observed versions and the action that saw it.

A new version can change idempotency, error codes or response fields, which are exactly what Quarter relies on to retry safely and to prove an outcome. Until someone checks, Quarter will not start new writes on untested behavior. While the block is open, new actions of that type fail with 422 ACTION_SPEC_NOT_CERTIFIED and error.details.specBlockId. Actions already in flight continue and reconcile as before.

Check that the provider change does not affect the action, for example in the provider's changelog, then clear the block with a reason. The clearance is audited.
