Recipes

Run a named business action, such as refunding an order or deleting an account, as one operation of protected steps with one signed proof.

A recipe is a named business action, such as order.refund or account.delete, that runs a fixed list of provider actions as one operation. You send one input. Quarter checks it, turns it into steps, and runs each step as an ordinary protected action with its own id, evidence and Outcome Proof. A step starts only after the step before it is proven CONFIRMED. When the operation ends you get one signed proof that covers every step.

Recipes are fixed and versioned. There are no conditions beyond skipping a step whose input you left out, no loops, and no code of yours inside them. Quarter does not look up provider ids for you: you pass the ids you already hold.

Like every action today, recipe steps run in sandbox projects until their ActionSpecs are certified. The delete actions used by account.delete, and the update actions used by customer.change_email, are preview specs and have not been run in the Provider Lab yet. See the actions reference.

The recipe format

A recipe is a JSON file of steps. A step's input is a literal, or a string that starts with $. and reads a path from the recipe input, such as "$.email". Two more forms let a step use what an earlier step made:

  • "$steps.N.providerObjectId" is the id of the object step N created, for example the Stripe customer id. It is filled in when that step is CONFIRMED, from the step's recorded evidence. It is the only value a step can read from an earlier step, and step N cannot be one that may be skipped.
  • A "..." key spreads an object from the input into a literal one, so a recipe can add fields to a row you supply. Keys written after it win.

Run a recipe

POST/v1/recipes/{name}/runAuth: API key

The body takes an id, an actor and the recipe's input. Derive the id from the business action, as you would an action id, for example delete-account:<userId>:v1. Step n runs as the action <id>:step:<n>, counting only the steps that run.

The response is the operation view plus recipe, the name@version that ran. Follow it with GET /v1/operations/{operationId}, or with the operation.* events. Each step also emits the usual action.* events under its step action id.

Onboard and change email

customer.onboard takes the customer's email, optional names, and a record that names your table, its onConflict column and the row to write. customer.change_email takes the new email and one block per system that holds it. Send only the blocks you use: a step whose block is missing is skipped.

List and describe recipes

GET/v1/recipesAuth: API key

GET/v1/recipes/{name}Auth: API key

Both return each recipe's name, version, summary, compensateOnFailure, its steps as { action, optional }, and its inputSchema as JSON Schema. An unknown name returns RESOURCE_NOT_FOUND (404).

Idempotency

  • The same id never runs twice. Sending the same id and input again returns the existing operation with 200 instead of 201, whatever state it is in.
  • The same id with a different input is refused with ACTION_ID_CONFLICT (409) and runs nothing.
  • Recipe ids and operation ids share one namespace in a project. Use a prefix per recipe.
  • A corrected input is a new business action: give it a new id, such as :v2.

When the input does not fit

Quarter checks the input against the recipe's inputSchema, then checks every step's input against that step's ActionSpec, before anything runs. A mismatch returns VALIDATION_FAILED (422). details.errors lists each problem, and a step problem names the recipe step and its action. Nothing is created, so fix the input and send it again with the same id.

When a step fails

account.delete, order.refund, subscription.cancel_and_notify and customer.change_email run with compensateOnFailure: false. When a step cannot be proven, the operation stops and later steps do not start. Nothing that already happened is undone. customer.onboard runs with compensateOnFailure: true, described below.

Step outcomeOperationWhat to do
NOT_EXECUTED, for example a provider rejectionFAILED, with a reason such as step 2 did not execute: ...Read the step's action. Fix the cause and run the recipe with a new id.
NEEDS_REVIEW, or the step used its retry budgetNEEDS_REVIEW, with a reason that names the stepResolve the step's action with POST /v1/actions/{actionId}/resolve. The operation then continues from that step.
OUTCOME_UNKNOWN or RECONCILINGRUNNINGWait. Reconciliation settles the step first.
Deletes cannot be undone. If a step of account.delete fails, the providers before it have already deleted their records. The run stops there so a person can look at it, and it never guesses at the rest.

The operation proof

GET/v1/operations/{operationId}/proofAuth: API key

Once the operation has finished (COMPLETED, FAILED, NEEDS_REVIEW or COMPENSATED), Quarter signs one manifest for it. body.steps lists each step's action id, action type, state and proofHash, the SHA-256 of that step's own Outcome Proof body. A step with no proof yet has no proofHash. While the operation is RUNNING or COMPENSATING the endpoint returns RESOURCE_NOT_FOUND (404).

Verify it offline

The operation proof is signed with the same Ed25519 key as action proofs, so it verifies with the same keys from GET /v1/proof_keys and the same procedure. To check a step, fetch that step's action proof and compare its body with the step's proofHash.

What customer.onboard proves

  • A Stripe customer and a Clerk user are created, then your row is upserted with stripe_customer_id and clerk_user_id set to the ids the providers returned. You do not pass those two ids.
  • If the row write fails, the customer and the user are deleted again, newest first (Clerk, then Stripe), each as its own protected action. When both deletes are proven the operation ends COMPENSATED.
  • If a delete cannot be proven, the operation stops in NEEDS_REVIEW for a person. It does not guess.
  • stripe.customer.create and clerk.user.create declare a delete of what they created. That is what makes the undo possible.

What customer.change_email proves

  • Clerk goes first. It only switches the primary email to an address the user already has and has verified, by its primaryEmailAddressId. An unverified change stops there, before Stripe, HubSpot or your row is touched.
  • Then Stripe, HubSpot and your own row, each by id, so no provider gains a second record. Each update is proven by reading the object back and comparing the fields.
  • Resend is not included. Resend cannot change a contact's email address, so this recipe leaves that contact alone.
  • There is no undo. Updates are not compensated, because Quarter does not hold the previous values. A failed step stops the run, and the steps before it stay applied.

What account.delete proves

  • Billing stops first: a Stripe subscription you pass is cancelled before anything is deleted. Your own row is removed last, so your app still knows the account until every provider is done.
  • Each record you name is deleted from its provider, and each delete is proven by a read by id that finds it gone. A read that still finds it proves a retry is safe, and the same step is sent again.
  • CONFIRMED on a delete step means the record is absent. It does not say this call removed it: an id that never existed, or belongs to another account, confirms the same way. Check the ids you pass.
  • Only the records you name are touched. Quarter does not search for other copies, and does not reach data a provider keeps outside that record, such as invoices, logs or backups.
