Integrate

Mirror to your database

Keep one row per user with their current access in your own Postgres or Supabase, and check access with a plain query.

With the mirror on, Quarter writes each user's current access into a table in your own Postgres or Supabase database whenever it changes. Your app, and the AI tool that writes its code, can check access with a query instead of an API call.

Turn it on

Give Quarter a Postgres connection string for a database user that can create and write one table. For Supabase, use the connection string from your project settings. The database must be reachable on a public address. Quarter tests the connection, creates the table, named quarter_access unless you choose another name, and writes a row for every user who already exists.

The connection string is stored encrypted, and is never shown again.

The table

ColumnWhat it holds
user_idYour own user id.
entitlementsThe names of the entitlements that are active now, sorted.
creditsBalances by currency, such as {"credits": 120}.
accessThe full access response.
updated_atWhen Quarter last wrote the row.

Check access

A user who has never bought anything has no row. Treat a missing row as no access.

With Supabase row-level security

Telling your AI tool

What the mirror is not

  • It is a copy, written a moment after each change. Use it to decide what to show, not to spend credits. Spend through the API, which is atomic.
  • Quarter only writes to it. Changes you make to the table are overwritten by the next change for that user.
  • When a user is erased, Quarter deletes their row too.

GET /v1/apps/{app}/mirror shows when the mirror last wrote and the last error, if any.
