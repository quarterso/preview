Outcomes

Verdicts

Every action and operation step carries a verdict: a failure class, whether a new attempt is safe, and the next step, derived only from evidence Quarter already recorded.

An action's state says where it is. Its verdict says what that means for you: what happened, whether you may try again, and what to do next. The same verdict is written for the engineer reading an action view, the agent reading a tool result, and the operator in the console.

A verdict is a projection of the action's history. It is computed from the state and the event that caused it, never from a guess, and it never claims more than that evidence shows. A settled verdict carries the evidence item that settled it.

The verdict object

FieldMeaning
classThe failure class, one of the values below.
retrySafetrue only when a new attempt provably cannot apply the effect a second time.
nextStepOne sentence: the safe next step, written so a person or a model can follow it.
evidenceOptional. The evidence item from the event that produced the current state.

Verdict classes

ClassWhat it meansRetry safeNext step
confirmedThe provider applied it.NoNothing to do.
settled_after_lost_responseA response was lost, and Quarter then settled the outcome with the provider. It says whether the effect was applied.Only when the provider never applied itApplied: do not retry. Not applied: retry the same action id (SAFE_TO_RETRY) or send it under a new id (NOT_EXECUTED).
rejectedThe input failed validation, or the provider refused the request. Nothing was applied.YesFix the request, then send it under a new action id.
deniedA policy or a reviewer refused it, so nothing was sent.YesResend only if that decision changes.
not_dispatchedThe request never reached the provider.YesRetry the same action id.
throttled_not_dispatchedThe provider rate-limited it before acting.YesRetry the same action id after the limit resets.
retry_budget_spentNothing was applied, and Quarter stopped retrying.YesFix the cause, then send it under a new action id.
not_executedNothing was applied.YesRetry the same action id when the state is SAFE_TO_RETRY; send it under a new action id when it is NOT_EXECUTED.
resolved_manuallyA person resolved it with evidence.Only when resolved as NOT_EXECUTED or SAFE_TO_RETRYFollow the person's note.
outcome_contradictedQuarter recorded it as not executed, and a verified provider event later said it took effect.NoDo not retry. Check the provider before doing anything else.
lost_responseThe response was lost and the outcome is not settled yet.NoDo not retry. Quarter is checking with the provider, or a person must resolve it with evidence.
awaiting_approvalA policy held it for a person. Nothing has been sent.NoApprove or reject it.
partialSome records were applied and some failed.NoA person must review it before anything is resent.
in_reviewThe outcome is uncertain and waits for a person.NoDo not retry. Resolve it with evidence.
blocked_version_driftAn operation step was not sent because the provider served a different API version than the spec expects.NoReview the spec and clear the block.
not_startedAn operation step that has not started. Nothing was sent.NoWait for the earlier steps.
in_progressQuarter is still working on it.NoWait. Do not resend it under a new action id.
compensatedIt was applied and then reversed.NoNothing to do.
Retry the same action id, or send a new one. From SAFE_TO_RETRY, retry with the same action id: Quarter runs the same action again. From NOT_EXECUTED, the action is final, so a new attempt needs a new action id, such as a bumped :v2 suffix. The nextStep sentence always says which.

How a verdict is chosen

  • A verified provider event that contradicts a NOT_EXECUTED outcome wins over everything else: outcome_contradicted.
  • A manual resolution comes next: resolved_manually, retry-safe only when the person resolved it as NOT_EXECUTED or SAFE_TO_RETRY.
  • Otherwise the state and the event that caused it decide. When a response was lost earlier and the provider then settled the outcome, the class is settled_after_lost_response, so you can tell it apart from a clean confirmation.
  • A policy hold (awaiting_approval) is told apart from an uncertain outcome (in_review). Only the first can be approved or rejected; the second is resolved with evidence. See Handling states.

Where verdicts appear

SurfaceWhere to find it
Action viewsverdict on every action returned by POST /v1/actions/execute, GET /v1/actions/{actionId}, GET /v1/actions, approve, reject and resolve. See the API reference.
Webhooksdata.verdict on every action event, such as action.confirmed and action.needs_review. See Webhooks.
Operation stepssteps[].verdict on an operation or recipe run. A step that has not started is not_started, or blocked_version_drift when a spec block stops it. See Operations.
Agent toolsquarterTool and quarter_tool put the class and the next step in the message the model reads and add verdict to the report. Unless the verdict is retry-safe, the model is told not to retry and not to call the tool again. See Agent tools.
MCPquarter_explain_action returns an action's state, verdict and a timeline summary to Claude Code, Cursor and other MCP clients. See AI coding tools.
Reliability by providerverdicts on GET /v1/stats/providers counts each provider's actions by class for the window.
The consoleEach action shows its verdict, and the provider view counts verdicts per provider.

Reading a verdict in code

Branch on retrySafe before you retry, and show nextStep to whoever acts next. The state still decides whether to reuse the action id.

Python exposes the class as verdict.class_, since class is a keyword. Observed calls get a lighter label, the call class, which is not a verdict and never evidence. See Capture and observed calls.
