NameTypeRequiredDescription

Stored from the provider response: id, object, deleted. Everything else is dropped before it leaves the executor.

Known limitations

  • Already absent is CONFIRMED: a delete answered 'not found' is classified ambiguous (errorCode already_absent), never a rejection, and the lookup that follows proves absence (evidence object_absent). CONFIRMED therefore means the object is absent, not that this action removed it; an object that never existed confirms the same way.
  • A lookup that still finds the object after a lost response proves SAFE_TO_RETRY: a repeated delete cannot duplicate an effect, and a retry that meets our own landed delete reads as already absent.
  • Irreversible: no compensator is declared and none can exist. Class AR3 because every ambiguous outcome is settled by a strongly consistent read by id.
  • Clerk accepts no idempotency key on delete; none is sent.
  • Any 404 on the delete or the read is read as absent, including a mistyped id.

Stored from the provider response: id, object. Stored as a hash: first_name, last_name, username, email_addresses. Everything else is dropped before it leaves the executor.

Known limitations

  • Convergent: re-applying the same values is harmless, so a lost response is settled by reading the object by id and comparing the intended fields (read_after_write, fields hashed). Equal proves CONFIRMED; the old values prove SAFE_TO_RETRY.

  • No compensator is declared: the previous values are not known to Quarter, so an update cannot be reversed from its own record.
  • A concurrent writer changing the same fields makes the read report a difference; the retry then overwrites that writer, which is the intended final state of this action.
  • A 404 on the update is a rejection (NOT_EXECUTED): an update never creates the object.
  • Clerk accepts no idempotency key on PATCH /v1/users/{user_id}; none is sent.
  • Changing the email is not one call on this endpoint. primaryEmailAddressId switches the primary to an email address object that already exists on the user and is verified. A new address first needs POST /v1/email_addresses (user_id, email_address, verified, primary), which creates an object and is not convergent, and the old address stays on the user until DELETE /v1/email_addresses/{id}. This action does only the switch.
  • Metadata is out of scope: Clerk API version 2026-05-12 removed public_metadata, private_metadata and unsafe_metadata from this endpoint in favour of /v1/users/{user_id}/metadata.

Known limitations

  • Already absent is CONFIRMED: a delete answered 'not found' is classified ambiguous (errorCode already_absent), never a rejection, and the lookup that follows proves absence (evidence object_absent). CONFIRMED therefore means the object is absent, not that this action removed it; an object that never existed confirms the same way.
  • A lookup that still finds the object after a lost response proves SAFE_TO_RETRY: a repeated delete cannot duplicate an effect, and a retry that meets our own landed delete reads as already absent.
  • Irreversible: no compensator is declared and none can exist. Class AR3 because every ambiguous outcome is settled by a strongly consistent read by id.
  • The column must carry a unique constraint; without one the filter deletes every matching row and Quarter cannot tell.
  • PostgREST has no idempotency key. With return=representation a delete that matched no row answers 200 with an empty list, which is read as already absent.
  • Row-level security can hide a row from both the delete and the read, which then reads as absent. Use the service role key, which bypasses it.
