Concepts

Action identity and fingerprints, the state machine, reliability classes, evidence and assurance, reconciliation, and Outcome Proof.

Quarter turns a provider write into a sequence: intent, policy, plan, dispatch, evidence, and then either a known outcome or an explicit statement that the outcome is not known yet. This page defines each part.

Action identity

Every action has an id that you choose. It names the business operation, not the HTTP request: refund:order_1042:v1, cancel-subscription:sub_9:2026-09. Build it from data your system already has, so any process that handles the same operation computes the same id.

  • Ids are unique per tenant, up to 255 characters, and can contain :.
  • Never include a timestamp, a random value or an attempt counter. A new id is a new write.
  • The version suffix (:v1) is for the rare case where the same business operation must genuinely run again, such as a second partial refund on one order.

Quarter derives the provider idempotency key from the project, the action id and the ActionSpec version pinned when the action was created. The key never changes between attempts. You never send an idempotency key yourself.

Fingerprints

Quarter hashes the canonical JSON of action, input and subject into fingerprint (sha256:<hex>). Sending an existing id with the same fingerprint returns the existing action. Sending it with a different fingerprint fails with ACTION_ID_CONFLICT (409) and nothing is dispatched. actor, metadata, policy and deadline are not part of the fingerprint.

States

An action is always in exactly one state. Only the ledger changes it, and every change is an append-only event.

StateMeaningFinal
CREATEDIntent recorded.No
VALIDATEDInput matches the ActionSpec schema.No
AUTHORIZEDPolicy allows it. Waiting for an executor to claim it.No
EXECUTINGA provider attempt holds a lease. No second attempt can start.No
CONFIRMEDThe intended effect exists at the provider. Backed by evidence.Yes
NOT_EXECUTEDProven not to have happened: invalid, denied, or rejected by the provider.Yes
OUTCOME_UNKNOWNThe attempt may have reached the provider and the response was lost.No
RECONCILINGQuarter is asking the provider what happened, within a bounded budget.No
SAFE_TO_RETRYEvidence shows the write did not take effect and another attempt is safe.No
NEEDS_REVIEWAutomation cannot decide safely. A person resolves it.No
COMPENSATINGA declared compensator is running.No
COMPENSATEDThe compensator completed.Yes

The main transitions: AUTHORIZED to EXECUTING; from EXECUTING to CONFIRMED, NOT_EXECUTED, SAFE_TO_RETRY, OUTCOME_UNKNOWN or NEEDS_REVIEW; from OUTCOME_UNKNOWN to RECONCILING; from RECONCILING to CONFIRMED, NOT_EXECUTED or SAFE_TO_RETRY, or to NEEDS_REVIEW when the budget runs out. A policy review sends a new action straight from VALIDATED to NEEDS_REVIEW.

An executor that crashes mid-attempt loses its lease. The action then becomes OUTCOME_UNKNOWN with reason LEASE_EXPIRED, because a crash before dispatch and a crash after dispatch look the same from outside.

Reliability classes

Each ActionSpec declares what Quarter can guarantee for that action with that provider. The class is a property of the provider's API, not a setting.

ClassNameGuarantee
AR0ObservedThe action is identified and logged. No correctness guarantee.
AR1Duplicate-resistantNo concurrent duplicate attempts. An ambiguous attempt is never retried automatically.
AR2Retry-safeProvider-native idempotency absorbs a retry under documented conditions.
AR3ReconcilableAfter an ambiguous attempt, Quarter determines the outcome from deterministic evidence within a bounded budget.
AR4RecoverableReconcilable, and a declared compensator exists. No current action is AR4.

ActionSpecs also carry a status: experimental, preview, assured or critical. Production projects accept only assured and critical specs.

Evidence and assurance levels

A state that claims an outcome (CONFIRMED, NOT_EXECUTED, SAFE_TO_RETRY) needs typed evidence. Each evidence record names its kind, the predicate it observed, the verifier that produced it, and an assurance level.

AssuranceMeaning
PROVIDER_NATIVEThe provider's own response or idempotency replay proves the outcome.
DETERMINISTIC_RECONCILIATIONA deterministic lookup or field comparison proves it.
HEURISTIC_RECONCILIATIONSuggestive but not conclusive. Recorded on the timeline; never finalizes a state.
MANUALAn operator resolved it with an attached, audited note.
UNRESOLVEDNo conclusion yet.

Which evidence proves what is fixed by the ActionSpec's evidenceRules, not by the adapter that collected it. For example, stripe.refund.create accepts provider_object_exists from dispatch, idempotency replay or a metadata lookup as proof of CONFIRMED, but a successful HTTP status alone proves nothing.

Reconciliation

When an attempt ends ambiguously (timeout, connection reset, 5xx, lost body), the action becomes OUTCOME_UNKNOWN and Quarter opens a reconciliation job. It runs the spec's reconciliation rules in order:

RuleWhat it does
native_idempotency_replayResends the identical request with the same idempotency key. The provider replays its stored result.
business_key_lookupLooks up the object by the action id Quarter wrote into provider metadata.
direct_object_lookupFetches the object by the client id Quarter chose for it. Found proves CONFIRMED; absent proves SAFE_TO_RETRY when the provider enforces that id as unique.
read_after_writeReads the object and compares the fields the action set.
bounded_list_matchLists recent objects in a time window and matches them. Heuristic unless the spec says otherwise.

Each spec sets a reconciliationBudget: a maximum number of provider calls, a maximum elapsed time, and a backoff. When the budget runs out without deterministic evidence, the action goes to NEEDS_REVIEW. Quarter never retries an ambiguous write it cannot prove safe.

Provider webhooks, when you configure them, are leads: a matching event is recorded as heuristic evidence and starts another reconciliation run. The deterministic lookup, not the webhook, decides the state.

Outcome Proof

Once an action reaches CONFIRMED, NOT_EXECUTED, SAFE_TO_RETRY, NEEDS_REVIEW or COMPENSATED, its view carries a proof. The proof lists all evidence, the assurance of the evidence that decided the state, and the specVersion, compilerVersion and planHash it was judged against. You can store it next to your own record of the operation.

The plan hash identifies the compiled plan exactly. Two actions with the same plan hash were run under the same dedupe strategy, retry rules, reconciliation rules and policy gates.
