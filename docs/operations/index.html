Build

Operations

Run several protected actions in order as one operation, reverse confirmed steps when a later one fails, and pause for review instead of guessing.

An operation is an ordered list of 1 to 20 steps. Each step is an ordinary protected action with its own id, plan, evidence and proof. The operation only decides what runs next. It is not a distributed transaction: a confirmed write is reversed by a second provider write, never rolled back.

For common business actions, such as refunding an order or deleting an account, a recipe builds the steps for you. A finished operation has one signed operation proof that covers every step.

Create an operation

Give the operation an id derived from the business operation, as you would an action id. Step n runs as the action <operationId>:step:<n>. A step takes action, input, and optionally subject and metadata. The actor is set once for all steps.

Each step in the view carries providerObjectId once the step is CONFIRMED: the id of the object the provider created or changed, taken from the step's evidence. A step that has not confirmed has null.

POST /v1/operations returns 201 when it creates the operation and 200 when the same id and steps already exist. The same id with different steps is refused with ACTION_ID_CONFLICT (409). Every step's action must have an active ActionSpec, or the request fails with ACTION_SPEC_NOT_FOUND before anything runs. Read the operation with GET /v1/operations/{operationId}.

How steps advance

  • A step starts only when every earlier step is CONFIRMED.
  • A step in SAFE_TO_RETRY is submitted again with the same action id. The evidence already proved a second attempt cannot duplicate it.
  • A step in OUTCOME_UNKNOWN or RECONCILING holds the operation in RUNNING until reconciliation settles it.
  • Advancing only reads step states and submits idempotent actions, so a crash or a second worker never runs a step twice.
Operation stateMeaning
RUNNINGA step is running or waiting for its outcome.
COMPLETEDEvery step is CONFIRMED.
FAILEDA step is NOT_EXECUTED and nothing needed reversing, or compensateOnFailure is off. reason names the step.
COMPENSATINGA step failed after earlier steps confirmed. Quarter is reversing them.
COMPENSATEDEvery confirmed step was reversed.
NEEDS_REVIEWA step needs a person, or a confirmed step cannot be reversed.

Compensation

With compensateOnFailure: true, when a step ends NOT_EXECUTED after earlier steps confirmed, Quarter reverses the confirmed steps in reverse order. Each reversal is a protected action of its own, run through the compensator the step's ActionSpec declares. For example, square.payment.create declares square.refund.create with the payment id and amount of the original.

Few ActionSpecs declare a compensator today. stripe.customer.create and clerk.user.create declare a delete of the object they created, which is what lets customer.onboard undo itself. If a confirmed step has none, the operation moves to NEEDS_REVIEW with a reason that names the step, and nothing is reversed automatically. Check for a compensation block in the step's ActionSpec (GET /v1/specs/{provider}/{action}) before you rely on it. You can also reverse one confirmed action yourself with quarter.actions.compensate(actionId, reason).

Review pauses

When a step ends NEEDS_REVIEW, the operation stops in NEEDS_REVIEW and later steps do not start. Resolve the step's action with POST /v1/actions/{actionId}/resolve, using the step's action id. The operation then continues from that step: CONFIRMED moves on to the next step, NOT_EXECUTED fails or compensates, and SAFE_TO_RETRY submits the step again.

Events

Operations emit their own events, delivered through webhooks and the event stream like action events. Each step also emits the usual action.* events under its step action id.

EventWhen
operation.completedEvery step confirmed.
operation.failedA step did not execute and nothing was reversed.
operation.compensatedEvery confirmed step was reversed.
operation.needs_reviewThe operation paused for a person.
