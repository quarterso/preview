How providers are supported

The three ways Quarter proves a provider write after a lost response, how it treats a conflict on its own id, and what the provider stages mean.

A supported provider has an adapter and at least one ActionSpec. What differs between providers is how a write can be proven after the response is lost. Quarter uses one of three proof paths, chosen per action from what the provider documents. Where none applies, the action is never retried automatically.

Key replay

The provider stores its response under an idempotency key. Quarter derives the key from your action id and sends it on every attempt. After a lost response it sends the identical request with the same key, and the provider returns the stored result without acting again. Some mark the replay, such as Mollie's Idempotent-Replayed header.

Replay is only used inside the retention window the provider documents: 30 days for Lithic, 7 days for Adyen, 72 hours for Checkout.com, 24 hours for Stripe, Resend, Plaid and Modern Treasury, about 3 hours for Bird, 1 hour for Mollie, Square and Shopify. PayPal, Xero, QuickBooks and Brex do not document retention, so Quarter replays within one hour only. Increase does not document it either, so Quarter never replays there.

Client identity plus lookup

Quarter derives an identifier from your action id and writes it into the object: a Clerk external_id, a Chargebee customer id, a Recurly account code, a Google Calendar event id, an Auth0 user_id, a Marqeta token, a Firestore document id. After a lost response it fetches the object by that identifier.

  • Found proves CONFIRMED.
  • Absent proves SAFE_TO_RETRY only when the provider enforces the identifier as unique, as Clerk, Chargebee, Recurly, Google Calendar, Auth0, Marqeta and Firestore do. A retry then cannot create a second object.
  • When the identifier is searchable but not unique, only a match is proof and absence goes to NEEDS_REVIEW. This covers Zendesk external_id, Postmark message metadata and Increase's list by idempotency_key.

Upsert plus read-back

The write creates or updates by a key you own, so repeating it leaves one record: a Salesforce external ID, a HubSpot contact by email, a NetSuite external ID, a Supabase row on a unique column, an Airtable record by its merge field. After a lost response Quarter reads the record back and compares the fields it set. A match proves CONFIRMED. A difference proves SAFE_TO_RETRY, because repeating the upsert is harmless.

The key must be unique in the provider. A Supabase onConflict column without a unique constraint lets PostgREST insert duplicates, and Quarter cannot tell.

A conflict on Quarter's id is proof, not failure

When Quarter chose the identifier, a retry after a lost response can come back as already exists: a Clerk 422, Chargebee duplicate_entry, a Recurly 422 for a taken code, a Google Calendar, Auth0, Marqeta or Firestore 409, or Increase idempotency_key_already_used_error. That conflict means the first attempt landed.

Quarter never treats it as a rejection and never records NOT_EXECUTED for it. The attempt is recorded with error code client_identity_exists, and reconciliation looks the object up to confirm it and record its id.
