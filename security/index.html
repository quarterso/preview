Security

Quarter keeps access. It never touches the money.

Quarter sits between the stores and your app. Here is what it does with what passes through, and what is not in place yet.

What Quarter never does.

Never holds your money

Payments stay in your own Stripe, Apple or Google account. Quarter never holds or moves money.

Never sees card data

Quarter reads store ids and events. Card numbers never reach it.

A read-only Stripe key

Quarter uses only a restricted key that can read. It cannot charge, refund or pay out.

Your user ids, nothing more

Quarter stores your own user ids, not names or emails.

Erasure and export

One call erases a user, and one call exports everything Quarter holds about them.

Built into the code today.

Each of these is in the API now. None of them is a plan.

Every store message is verified

Stripe webhooks are checked against your signing secret. Apple's signed data is checked against Apple's certificates. Google notifications must carry a secret token, and are then confirmed with the Play API.

Secrets are sealed

Store keys, webhook secrets and your mirror connection string are encrypted with AES-256-GCM. Webhook secrets are shown to you once.

Tenants are isolated in the database

PostgreSQL row-level security confines every API request to your organization, on top of the checks in the code.

Webhooks are signed

HMAC SHA-256 over a timestamp and the raw body. Deliveries go only to public https URLs and never follow redirects.

Test and live never mix

A key's prefix must match its project's environment, and a test project takes only Stripe test keys.

Only what access needs

Stripe and Google records keep only the fields Quarter reads. Names, emails and addresses are dropped before anything is stored.

A record you can follow.

  • Every store record is stored once and never changed, so access can always be traced to what the store said
  • Store records are kept for your retention setting, seven years by default as tax evidence, then deleted
  • Events are append-only
  • Setup changes and erasures are written to an audit log, with the key that made them
  • API keys are stored only as hashes
  • The authorization header is removed from request logs

What is not in place yet.

Quarter is pre-launch. We would rather you hear it here than find it later.

  • Sign-in, roles and single sign-on for the console
  • Self-serve key management. Quarter issues keys during early access
  • A data processing agreement and a published sub-processor list
  • Third-party audits or certifications
