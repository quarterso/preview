Reconciliation

Your refund call timed out. Quarter asks Stripe what happened.

Nothing retries until Quarter knows. It runs the checks each provider allows, and settles only on hard evidence.

CONFIRMED
Budget 2 of 5 calls
  1. 1Replay the idempotency keyStripe answered 503. No evidence either way
  2. 2Look up by business keyRefund re_3Qx…7Lk found by its action metadataprovider_object_exists
Outcome ProofCONFIRMED · DETERMINISTIC_RECONCILIATIONRetry suppressed. No second refund.

Illustrative example

5 checks, chosen per action.

native_idempotency_replay

Replay the idempotency key

Resend with the same provider key. The provider returns the original result.

Used by 27 actions

business_key_lookup

Look up by business key

Search the provider for the object by a key Quarter attached to it.

Used by 6 actions

direct_object_lookup

Look up by id

Fetch the object by its id. For a create with a unique id, absence proves a retry is safe.

Used by 13 actions

read_after_write

Read back and compare

Fetch the record and compare the fields the write was meant to set.

Used by 16 actions

bounded_list_match

Bounded list match (narrows only)

Match recent objects on content. Narrows an incident. Never proves an outcome.

Used by 4 actions

A fixed budget, then a person.

Shopify details

  • Only deterministic evidence closes an action

    A provider record proves it. A guess never does, and goes to a person.

  • 5 calls in 90 seconds, then a person

    The budget for 56 actions. When it runs out, the action goes to NEEDS_REVIEW with the evidence so far.

  • Twilio stays in the lab

    Only a list match is possible, so its budget is 2 calls in 30 seconds and it never finalizes on its own.

  • Proof can run out

    In the simulator lab, shopify.order.cancel settled 63% of lost responses and sent the rest to review, as intended.
